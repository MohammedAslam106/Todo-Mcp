# Todo App

A full-stack, type-safe todo app with Google/GitHub sign-in, server-rendered React, and a built-in [MCP](https://modelcontextprotocol.io) server so AI assistants like Claude can manage your tasks.

- **[TypeScript](https://www.typescriptlang.org)** end-to-end, **[pnpm](https://pnpm.io)** as the package manager
- **[Fastify 5](https://fastify.dev)** HTTP server, run directly from `.ts` via [`tsx`](https://tsx.is)
- **[Zod](https://zod.dev) + [fastify-type-provider-zod](https://github.com/turkerdev/fastify-type-provider-zod)**: one schema per route drives validation, serialization, *and* the OpenAPI docs at `/docs`
- **[@fastify/react](https://vite.fastify.dev/react/) + [@fastify/vite](https://github.com/fastify/fastify-vite)**: server-rendered React 19 + React Router 7 with file-based routing
- **[@fastify/oauth2](https://github.com/fastify/fastify-oauth2)**: sign in with **Google** or **GitHub** (no passwords), then a JWT session cookie via **[@fastify/jwt](https://github.com/fastify/fastify-jwt)**
- **PostgreSQL** via **[Drizzle ORM](https://orm.drizzle.team)**: typed schema in `db/schema.ts`, migrations generated by `drizzle-kit`
- **[Tailwind CSS v4](https://tailwindcss.com)** + **[shadcn/ui](https://ui.shadcn.com)** components

## Getting started

Follow these steps once to run the app on your machine. It takes about 15 minutes, most of it creating the Google/GitHub OAuth apps.

### 1. Install the prerequisites

| Tool | Version | How to get it |
|---|---|---|
| Node.js | 22 or newer | <https://nodejs.org> (check with `node -v`) |
| pnpm | 9 | `corepack enable` (ships with Node), or `npm install -g pnpm` |
| PostgreSQL | 15 or newer | Windows/macOS installer from <https://www.postgresql.org/download/>, `brew install postgresql@16` on macOS, or `sudo apt install postgresql` on Debian/Ubuntu |

Make sure the PostgreSQL server is running and you know the password of the `postgres` superuser (the installer asks for it).

### 2. Install dependencies

```bash
cd project-2
pnpm install
```

### 3. Create the database

Create a dedicated role and database for the app. Open `psql` as the superuser:

```bash
psql -U postgres
```

then run (pick your own password):

```sql
CREATE ROLE todo_app_user WITH LOGIN PASSWORD 'choose-a-password';
CREATE DATABASE todo_app OWNER todo_app_user;
\q
```

The app role must **own** the database: migrations create their own `drizzle` schema to track what has been applied.

> On Windows, if `psql` isn't found, use the full path (e.g. `"C:\Program Files\PostgreSQL\16\bin\psql.exe" -U postgres`) or open **SQL Shell (psql)** from the Start menu.

### 4. Create your `.env`

```bash
cp .env.example .env            # PowerShell: Copy-Item .env.example .env
```

Then fill in:

| Variable | Value |
|---|---|
| `DATABASE_URL` | `postgresql://todo_app_user:choose-a-password@localhost:5432/todo_app` (the password from step 3) |
| `JWT_SECRET` | A long random string. Generate one with `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"` |
| `APP_URL` | `http://localhost:3000`. The address you open the app on; OAuth callbacks are built from it |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | From step 5 |
| `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` | From step 5 |

`PORT` (default `3000`) and `NODE_ENV` can stay as they are. `.env` is git-ignored; never commit it.

### 5. Create the Google and GitHub OAuth apps

The app has no passwords, so you need **at least one** of these. The login page only shows the providers you configure.

**Google**

1. Open [Google Cloud Console → APIs & Services → Credentials](https://console.cloud.google.com/apis/credentials) and pick (or create) a project.
2. If asked, configure the **OAuth consent screen**: user type *External*, fill in the app name and your email. While it is in *Testing*, add every Google account that should be able to sign in under **Test users**.
3. **Create credentials → OAuth client ID → Web application**.
4. Under **Authorized redirect URIs** add exactly:
   ```
   http://localhost:3000/api/auth/google/callback
   ```
5. Copy the client ID and secret into `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`.

**GitHub**

1. Open [GitHub → Settings → Developer settings → OAuth Apps](https://github.com/settings/developers) → **New OAuth App**.
2. **Homepage URL**: `http://localhost:3000`
3. **Authorization callback URL** (exactly):
   ```
   http://localhost:3000/api/auth/github/callback
   ```
4. Register it, then **Generate a new client secret**. Copy the Client ID and secret into `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET`.

A GitHub OAuth app allows only one callback URL, so use a separate GitHub app for any other address you run the app on. If you change `PORT` or `APP_URL`, update the callback URLs to `<APP_URL>/api/auth/<google|github>/callback` to match.

### 6. Create the tables

```bash
pnpm run migrate
```

This applies the Drizzle migrations in `db/migrations/`. It is safe to run again at any time; it only applies what's missing.

### 7. Start the app

```bash
pnpm run dev
```

When it's ready, the terminal shows:

```
    Todo App is ready.

    1. Open http://localhost:3000/connect in your browser
    2. Sign in with Google or GitHub
    3. Create a token and add the server to Claude (or any MCP client)

    MCP endpoint: http://localhost:3000/mcp
```

Open **<http://localhost:3000>** and sign in. Your first sign-in creates your account. Signing in later with the other provider using the same verified email address logs you into the same account.

> Use `localhost`, not `127.0.0.1`: the address must match `APP_URL` and the registered callback URLs, or the sign-in cookies won't be sent back.

To run the optimized production build instead of the dev server:

```bash
pnpm run build   # type-checks, then builds the client + SSR bundle into client/dist
pnpm run start
```

### Troubleshooting

| Symptom | Fix |
|---|---|
| Startup warning *"No sign-in providers are configured"* / login page says no providers | Fill in at least one `*_CLIENT_ID` + `*_CLIENT_SECRET` pair in `.env` and restart. |
| `JWT_SECRET is not set` | Set `JWT_SECRET` in `.env` (step 4). |
| `password authentication failed` / `ECONNREFUSED` on `migrate` or startup | Check that PostgreSQL is running and that `DATABASE_URL` matches the role, password and database from step 3. |
| `permission denied for database` on `migrate` | The role must own the database: `ALTER DATABASE todo_app OWNER TO todo_app_user;` |
| Google: *"Error 400: redirect_uri_mismatch"* | The redirect URI in Google Cloud must be exactly `http://localhost:3000/api/auth/google/callback` (no trailing slash, `localhost` not `127.0.0.1`). |
| Google: *"Access blocked: app has not completed verification"* | Add your Google account as a **Test user** on the OAuth consent screen. |
| GitHub: *"The redirect_uri is not associated with this application"* | Set the GitHub app's callback URL to exactly `http://localhost:3000/api/auth/github/callback`. |
| Back on the login page with *"Could not sign in with …"* | The server log has the details. Usually a wrong client secret, or you opened the app on a different address than `APP_URL`. |
| *"Your GitHub account has no verified email address"* | Verify the primary email in GitHub → Settings → Emails. |
| Port 3000 already in use | Set `PORT=3001` **and** `APP_URL=http://localhost:3001` in `.env`, and update both callback URLs. |

## Connecting an AI assistant (MCP)

The app is also an MCP server, so Claude Desktop, Claude Code, MCP Inspector and other clients can read and manage your todos and projects. The tools call the same `services/` functions as the REST API, so behavior and per-user scoping are identical.

**The easy way:** open **<http://localhost:3000/connect>** (also in the sidebar as "Connect AI assistant"), create a token, and copy the ready-made setup for Claude Code, Claude Desktop, or other clients.

### API tokens

MCP clients can't use the browser cookie, so they send a personal API token as `Authorization: Bearer <token>`. Tokens look like `todo_…`, are shown once at creation, and are stored only as a SHA-256 hash. Besides `/connect`, you can create one from the command line (the user must have signed in once):

```bash
pnpm run mcp:token you@example.com "Claude Desktop"
```

or, while signed in, via `POST /api/tokens` with `{ "name": "Claude Desktop" }` (`GET /api/tokens` lists them, `DELETE /api/tokens/:id` revokes).

### Option A: remote (Streamable HTTP) at `/mcp`

Runs inside the main server, so there's nothing extra to start. Stateless JSON mode: `POST /mcp` only (`GET`/`DELETE` return 405).

```bash
claude mcp add --transport http todo http://localhost:3000/mcp --header "Authorization: Bearer todo_..."
```

Or try it in the MCP Inspector: `npx @modelcontextprotocol/inspector`, transport "Streamable HTTP", URL `http://localhost:3000/mcp`, and add the `Authorization` header.

### Option B: local (stdio)

`mcp/stdio.ts` connects to Postgres directly (using `.env`), so the web server doesn't need to be running. Claude Desktop config (`claude_desktop_config.json`):

```json
{
  "mcpServers": {
    "todo": {
      "command": "pnpm",
      "args": ["--dir", "/absolute/path/to/project-2", "run", "--silent", "mcp:stdio"],
      "env": { "TODO_API_TOKEN": "todo_..." }
    }
  }
}
```

### Tools

| Tool | What it does |
|---|---|
| `todo_get_overview` | Counts: open/completed, overdue, due today, completed in the last 7 days, open by priority |
| `todo_list_todos` | Filter by `project_id` (or `"inbox"`), `status`, `priority`, `due` (`overdue`/`today`/`upcoming`/`none`), `search`; paginated with `limit`/`offset` |
| `todo_get_todo` / `todo_create_todo` / `todo_update_todo` / `todo_delete_todo` | Todo CRUD (`update` only changes the fields passed; `null` clears) |
| `todo_complete_todo` | Mark done, or re-open with `completed: false` |
| `todo_list_projects` / `todo_get_project` / `todo_create_project` / `todo_update_project` / `todo_delete_project` | Project CRUD (delete cascades to the project's todos) |

Tools carry `readOnlyHint`/`destructiveHint` annotations and return both JSON text and `structuredContent`. `due`-based filters accept an optional `today` (YYYY-MM-DD) so "today" matches the user's timezone rather than the database's.

### Why `tsx` instead of a `tsc` build for the server

The server runs straight from TypeScript source via `tsx` (an esbuild-based runtime) for both `dev` and `start` — there's no `dist/server` compile step. `pnpm run build` still runs `tsc --noEmit` first as a full type-check gate, and `pnpm run typecheck` runs that on its own (wire it into CI). This keeps the workflow simple and avoids ESM/`.js`-extension bookkeeping in relative imports, while still getting full type safety.

### Zod-driven validation, serialization & docs

Every route schema (`schemas/auth.ts`, `schemas/todos.ts`, `schemas/common.ts`) is a Zod object, used for three things at once:

1. **Request validation** — `server.setValidatorCompiler(validatorCompiler)` (from `fastify-type-provider-zod`) validates `body`/`params` against the Zod schema; invalid input gets a `400` with Zod's error messages.
2. **Response serialization** — `server.setSerializerCompiler(serializerCompiler)` validates and serializes the response against the Zod schema declared per status code. This is intentionally strict: e.g. `created_at`/`updated_at` use `z.iso.datetime()`, so `db/schema.ts` declares `TIMESTAMPTZ` columns with a small custom Drizzle type that reads them back as ISO strings to match.
3. **OpenAPI schema generation** — `@fastify/swagger` is registered with `transform: jsonSchemaTransform`, which converts the same Zod schemas into the OpenAPI document served at `/docs`.

Route handlers are typed via `FastifyPluginAsyncZod` (from `fastify-type-provider-zod`), so `req.body`, `req.params`, and the reply's expected shape are all inferred automatically from the Zod schemas — no manual typing or casting in the handlers.

Types inferred from the same schemas (`z.infer<...>`) are exported from `schemas/` and imported by the client (`client/lib/api.ts`, pages) as `import type`, so the frontend and backend share one source of truth for API shapes.

Interactive OpenAPI docs are served at **<http://localhost:3000/docs>** (raw JSON at `/docs/json`).

### Database

The schema lives in **`db/schema.ts`** (Drizzle ORM), and all queries in `services/` go through Drizzle's typed query builder:

```
users(id, email UNIQUE, name, avatar_url, created_at)
accounts(id, user_id -> users.id, provider ('google'|'github'), provider_account_id, created_at,
         UNIQUE(provider, provider_account_id))
projects(id, user_id -> users.id, name, description, color, created_at, updated_at)
todos(id, user_id -> users.id, project_id -> projects.id NULL, title, description,
      is_completed, priority ('none'|'low'|'medium'|'high'), due_date DATE, completed_at,
      created_at, updated_at)
api_tokens(id, user_id -> users.id, name, token_hash UNIQUE, created_at, last_used_at)
```

Deleting a project cascades to its todos. A todo with `project_id = NULL` lives in the Inbox. `DATE` columns are plain `YYYY-MM-DD` strings and `TIMESTAMPTZ` columns ISO 8601 strings (see `db/schema.ts`). Project `color` is one of `chart-1`…`chart-5`, mapped to the theme's chart tokens so it adapts to dark mode.

**Changing the schema:** edit `db/schema.ts`, run `pnpm run db:generate` (drizzle-kit writes a new SQL file + snapshot to `db/migrations/`), review the SQL, then run `pnpm run migrate`. Applied migrations are tracked in `drizzle.__drizzle_migrations`, so `pnpm run migrate` is safe to re-run. `pnpm run db:studio` opens Drizzle Studio to browse the data.

**Databases created before Drizzle** (tracked in the old `schema_migrations` table) are adopted automatically: `pnpm run migrate` marks `0000_baseline` as applied (it is exactly what the old SQL files built), drops `schema_migrations`, then applies the rest. Existing users, projects, todos and tokens are kept; only `password_hash` goes away.

### Authentication

Sign-in is **Google or GitHub only** (OAuth 2.0 via `@fastify/oauth2`). There are no passwords.

- `GET /api/auth/google` / `GET /api/auth/github` (optionally `?next=/connect`) redirect to the provider. `@fastify/oauth2` sets short-lived httpOnly cookies for the CSRF `state` (plus the PKCE verifier for Google) and checks them on the way back.
- The provider redirects to `/api/auth/<provider>/callback`. The server exchanges the code, fetches the profile, and finds or creates the user (`services/users.ts`):
  1. the user already linked to that Google/GitHub account, else
  2. the user with the same **verified** email, so one person can use both providers, and accounts from the old email/password days are picked up on first sign-in, else
  3. a new user.

  Only Google's `email_verified` address and GitHub's primary verified address (`/user/emails`) are trusted. An account without one is refused with a message on the login page.
- It then signs a JWT (`@fastify/jwt`), sets it as an **httpOnly, sameSite=lax** cookie named `token` (`secure` when `APP_URL` is `https://…`), and redirects to `next` (same-origin paths only) or `/`. Failures redirect to `/login?error=…`.
- Protected routes use a `server.authenticate` preHandler (`plugins/auth.ts`) that calls `req.jwtVerify()`, which reads the token from the cookie. `req.user` is typed via module augmentation in `types/fastify.d.ts`.
- Other endpoints: `GET /api/auth/providers` (which buttons to show: only providers with credentials configured), `POST /api/auth/logout`, `GET /api/auth/me` (current user with `name`/`avatar_url`; 401 if not signed in).
- `/api/projects/*` and `/api/todos/*` (GET/POST/PATCH/DELETE) all require authentication and are scoped to the logged-in user's `id`. `GET /api/todos?project_id=<id|inbox>` filters by project; assigning a todo to a project the user doesn't own returns `400`. Todo `PATCH` only updates the fields sent, so `null` explicitly clears `description`/`due_date`/`project_id`.

### UI

- Pages (all redirect to `/login` if not authenticated):
  - `/` **Dashboard**: stat tiles (open, due today, overdue, completed this week), 14-day completions chart, overall progress + open-by-priority, "Up next" list, per-project progress
  - `/inbox`, `/today` (due today + overdue), `/upcoming` (grouped by date), `/completed` (grouped by completion day)
  - `/projects/:id`: project progress + its task list; edit/delete from the header or the sidebar
  - `/login`: "Continue with Google / GitHub" (uses the `auth` layout). Signing in for the first time creates the account.
- Task lists have quick-add, Active/Done/All tabs, a text filter, and sorting (newest, due date, priority, title). Tasks support description, priority, due date, and project; edits are optimistic with rollback, and deletes can be undone from the toast.
- Global: collapsible sidebar (`Ctrl/⌘+B`), command palette (`Ctrl/⌘+K`), light/dark/system theme.
- Styling: Tailwind CSS v4 with a shadcn-style CSS-variable theme (`client/base.css`) — tokens like `bg-background`, `text-foreground`, `bg-primary`, etc.
- Components in `client/components/ui/` are installed directly from the official shadcn registry (`pnpm dlx shadcn add button input label card checkbox`, run again any time to update) rather than hand-written, per project convention. `components.json` is configured with `"tsx": true`, style `new-york`, and the `@/` path alias (see `vite.config.ts` / `tsconfig.json`). One rule enforced project-wide: no `space-x-*`/`space-y-*` — use `flex ... gap-*` instead (registry components are checked and fixed for this after every `add`).
- **The `new-york` registry ships Tailwind v3 syntax.** After every `add`, convert CSS-variable arbitrary values like `w-[--sidebar-width]` to v4's `w-(--sidebar-width)` (v4 treats the v3 form literally, so e.g. the sidebar overlaps the page), and replace any `theme(spacing.N)`. `grep -rn '\[--' client/components/ui` should return nothing.
- **Don't add `postcss-preset-env` back to `postcss.config.ts`.** It rewrote Tailwind v4's `color-mix(… var(--x) …)` output into static light-theme colors (breaking `bg-primary/20`-style opacity modifiers and dark mode) and polyfilled cascade layers with `:not(#\#)` specificity hacks. Tailwind v4 already handles prefixing/lowering via Lightning CSS.

#### `base.css` must use Tailwind v4's `@import` syntax

`client/base.css` starts with:

```css
@import "tailwindcss";
```

**Do not** change this to the Tailwind v3-style three directives (`@tailwind base; @tailwind components; @tailwind utilities;`). This was actually a real bug shipped in this project for a while: with `@tailwindcss/postcss` v4 installed, the old v3 directives don't load Tailwind's built-in default theme (the entire spacing scale, font-size scale, sizing scale) — only whatever is explicitly declared in this file's own `@theme` block (which here is just color and radius tokens). The practical symptom was that colors, borders, and border-radius worked (since those come from our own `@theme` block), but **every** `p-*`/`m-*`/`gap-*`/`size-*`/`h-*`/`w-*`(numeric)/`text-sm`/`text-xs`-type utility silently produced no CSS at all, sitewide — making every page look cramped and "barely styled" with no layout bug or error anywhere in the console. If you ever see that symptom again, check this line first before anything else.

## Windows note: patched Vite dependency

`pnpm run dev` on native Windows needs a one-line patch to `vite`. It is applied automatically by `pnpm install` (`patchedDependencies` in `package.json`, file `patches/vite@8.3.0.patch`), so there is nothing to do manually. Background, for anyone touching this later:

- **The bug:** `@fastify/react` registers its client-side route table as a virtual module with id `/$app/routes.js`, whose code contains `import.meta.glob('/pages/**/*.{jsx,tsx}')`. Vite's `import.meta.glob` transform (`transformGlobImport` in `vite/dist/node/chunks/node.js`) computes each match's specifier via `path.posix.relative(path.posix.dirname(id), file)`, treating `id` as if it were a real absolute filesystem path with a real parent directory. `/$app/routes.js` is a *virtual* id — it isn't recognized as one by Vite's `isVirtualModule()` helper (which only checks for a `virtual:` prefix, a null-byte prefix, or "no slash at all"), so it falls through to being treated as real.
- On Windows, Node's `path.posix` functions fall back to a `cwd()` helper that **strips the drive letter** when no absolute-looking (per POSIX rules — i.e. leading `/`) segment is present among the inputs. Since the matched page file's absolute path (`D:/aslam/.../client/pages/login.tsx`) doesn't start with `/` (it starts with a drive letter), `path.posix.relative` silently prepends this drive-letter-stripped cwd, concatenating the project path with itself and corrupting the resulting specifier (e.g. `/aslam/.../project-2/D:/aslam/.../project-2/client/pages/login.tsx`). This is POSIX-only path-joining behavior, so it never bites on macOS/Linux/WSL — only on native Windows.
- **The fix (`patches/vite@8.3.0.patch`):** teach `isVirtualModule()` to also treat any Windows root-relative id that isn't shaped like a real absolute Windows path (`/^\/[A-Za-z]:[\\/]/`) as virtual:
  ```diff
    function isVirtualModule(id) {
  -   return id.startsWith("virtual:") || id[0] === "\0" || !id.includes("/");
  +   return id.startsWith("virtual:") || id[0] === "\0" || !id.includes("/") || (isWindows && id[0] === "/" && !/^\/[A-Za-z]:[\\/]/.test(id));
    }
  ```
  This makes the glob-import transform skip the buggy directory-relative computation for ids like `/$app/routes.js`, which is what fixed it.
- Pinned to the exact resolved `vite@8.3.0`; if `pnpm update` moves to a newer Vite version, `pnpm install` will report the patch failed to apply (rather than silently dropping it or silently applying wrongly) — at that point, check whether upstream has fixed `isVirtualModule` for this case and drop the patch if so.
